# Agent 执行错误与会话恢复

单轮请求失败不应永久阻断后续消息。main、队伍、信道、TalkTo、任务、定时任务及观测通知共用以下规则：

- 已收到完整 ACP prompt 错误响应，且结构化上游错误为 429、500、502、503、504、SERVICE_UNAVAILABLE 或 RATE_LIMIT_EXCEEDED，同时运行进程仍存活：先结束错误输出，再恢复 READY。失败请求不自动重跑；后续消息与收件队列可继续执行。
- 传输中断或未识别的错误：客户端保留 ERROR。下次投递在状态检查前调用 `prepareForMessage()`，关闭故障运行时，并通过显式 `session/load` 恢复当前 session ID，成功后再投递。
- 恢复失败、缺少 session ID 或 Provider 不支持 session/load：明确拒绝执行，保留原会话身份和 ERROR，允许再次尝试或手动新建；不回退到空白新会话。
- main 的手动新建入口允许 READY、SLEEP、ERROR，直接启动新的客户端和上下文。新客户端启动失败时旧客户端、索引及 generation 不变。BUSY 仍拒绝替换。
- 队伍成员的状态投影与恢复结果同步。企微恢复失败返回反馈，不将该条消息当成已成功排队。
- 定时任务仍遵守既有分组会话规则，当前失败执行仍记为失败。观测只在结果变化通知投递时恢复 Agent，脚本执行位置、基线和重试规则不变。

正常睡眠唤醒继续遵守原自动轮转规则；严格恢复 ERROR 会话不采用睡眠唤醒的恢复失败后新建策略。该恢复不承诺失败请求已执行的工具事务回滚，也不自动重新执行失败请求。
